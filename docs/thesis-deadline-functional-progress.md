## Delivered in this increment

An opt-in fictional input desk now provides real API operations and a standalone page at `/prototype/inputs` through `routers.prototype_inputs.create_app(inputs, identity_db)`. It is not registered in ordinary `main.py`, does not launch a worker and has no default institutional provider.

- **Faculty-owned preference revisions:** authenticated faculty can load/save only the numeric faculty code explicitly bound to their server-side fictional grant. Existing strict `FacultyPreferenceUpdate` is reused. Explicit eligibility and offered-subject membership, unique days/ranks and the existing clock-range validator are enforced. Priority is read-only; missing preferences do not remove faculty. Exact subject/general meeting-block editing is explicitly rejected until its existing complete-pattern metadata validator is connected to the frozen catalog; no incomplete block is silently accepted.
- **Chair-controlled coefficients:** only an explicit, current, department/term/catalog-scoped `DEPARTMENT_CHAIR` grant permits approval. Existing admin/faculty account roles alone grant none of this authority. The eleven configurable fields are existing original-equation penalty coefficients: subject, time, day, preparation, load-balance, daily-load, gap, lecture/lab, underload, overload and heavy overload. Zero is preserved. Values are strict nonnegative integers bounded at 100000 for this prototype's input envelope, not recommended institutional weights. Targets, maxima, workload steps, eligibility, specialization terms and algorithms cannot be edited through this API.
- **Immutable persistence:** revisions use compare-and-swap, actor/nonce idempotency, an immutable SQLite chain, update/delete rejection, and authorization rechecking before commit. A new `inputs.sqlite3` is created only in a new owned temporary prototype root. Reopen, concurrent writers, corruption, expiry, wrong scope, replay, revocation and rollback are tested. No existing schema, dataset or application store is migrated.
- **Scheduling-input preparation:** a separately granted scheduler pins the exact minimum revision/digest, Chair coefficient revision/digest and all roster preference revisions. Both disposable policy stores are locked for the preparation transaction. A new immutable bundle is built using the existing capture codec; it retains every faculty, eligibility/calendar/template relationship, fixed non-teaching inputs and original search configuration. Preference keys remain integers as required by the original scorer. Original source dataset identity and minimum-policy provenance remain in the preparation record. The complete canonical bundle is stored privately with its hash and survives service/listener reconstruction. Later preference/weight revisions never rewrite it.
- **Existing loader integration:** a test registers the new bundle in an explicitly fictional verified catalog and passes it through the unchanged `CaptureAdapter` and `Session` constructor. This proves structural admission/preflight compatibility, **not optimizer execution**. The API reports `optimizer_consumption=NOT_ESTABLISHED`, `worker_started=false` and `SERVER_CATALOG_REQUALIFICATION_REQUIRED_NO_AUTOMATIC_ADMISSION`. It does not mark a prepared bundle CURRENT or grant run authority.
- **Real frontend operations:** the page calls the actual preference, Chair approval and preparation endpoints; it uses original workload CSS, text rendering, busy-state serialization, revision selectors, stale faculty-selection rejection, error messages and preparation reload. It has no pretend Start, publication, Saved Best or Restore control. Browser acceptance is still unexecuted; JSON editors are a minimal functional interface rather than a cosmetic redesign.

A separate **fictional demonstration fixture** provides 12 offerings/36 units, with disjoint explicit eligibility: Faculty 1 has 12 eligible units and Faculty 2 has 24. Explicit minima are 12 and 24 respectively. A constructed six-day witness passes the original publication validator and the captured-minimum qualifier, with assignments `[12,24]`. It establishes a hard-valid fictional input/witness, **not a generated schedule** or institutional eligibility. The existing infeasible 12-eligible-versus-24-minimum fixture is preserved. Original search may still fail or exhaust its bound; no success is fabricated and no academic eligibility is changed to rescue a real dataset.

## Shortest defensible seven-day architecture

**NO-GO today.** Keep the existing 600-second worker ceiling and physical Job Object/resource supervision. Existing E is 60 seconds; K's `Limits.validate` also caps total generations at 20, the worker admits population ≤8, and registration sets a run-wide deadline of admission time plus its wall budget. `claim` rejects an expired deadline or exhausted cumulative `spent`; `save` also enforces both. Pausing/resuming does **not** reset that lifetime budget. Retained checkpoints, process attempts and observation/export sizes are separately capped. `retention_plan` deliberately returns cleanup disabled. Repeatedly calling resume or starting new runs cannot honestly supply one 168-hour trajectory.

Recommend a **separately versioned fictional research-experiment supervisor**, reusing the original bundle consumer/checkpoint codec and existing physical process machinery. This is an implementation design, not a deployed continuation bridge or permission to bypass old admission:

1. Freeze one experiment ID, one logical optimizer run ID, exact canonical bundle bytes, scoring-policy/weight/minimum/preference snapshots, original engine/optimizer fingerprints, Python/library release and initial RNG state. Store private state in the new owned research realm; public evidence exports hashes, not raw credentials/receipts. Do not recapture a new bundle every segment.
2. Approve a fixed, explicit generation horizon and stopping policy **before** capture. Original checkpoints bind the complete parameters; raising generations after resume is rejected, not migrated. Existing 20-generation admission cannot be repurposed silently: a new versioned operational admission/store contract is needed while the old engine and worker remain unchanged. Preserve original stopping behavior; if the original GA finishes early, record completion. Running meaningless fresh runs or suppressing termination to fill seven days is not authorized.
3. Run bounded segments under the unchanged **≤600-second ceiling**, retaining existing CPU/private-memory/cleanup limits unless separately qualified. A wall-time budget is a guard, not a guarantee a generation finishes. Stop at original generation/checkpoint boundaries, capture full population, best-ever, histories and RNG, then verify child exit before admitting the next segment. If a generation cannot reach a safe boundary within its guard, retain the last committed checkpoint and fail honestly; do not increase timeouts to hide it.
4. Separate the experiment's 168-hour UTC horizon, active compute time, paused/downtime and per-segment budget. A full 168 hours of active work would need at least **1,008 full 600-second segments**, often more; this is arithmetic, not an execution benchmark. At each segment restore **the same** original checkpoint/run/bundle/configuration and advance generation/sequence/parent exactly once. Fitness history contains actual committed observations only. A segment is not a new randomized GA run.
5. Use an exclusive durable experiment owner lease/fence and monotonic commit sequence. Atomically commit the checkpoint hash, parent, generation, result/best projection, segment status and consumed-input proof. A separate trusted tip/freshness anchor is necessary: hashing a replaced checkpoint and replaced SQLite pin together does not authenticate recovery. After a crash, verify source/runtime/configuration, ownership, tip/lineage and independent anchor before restoring. Lost acknowledgements are reconciled, not relaunched blindly. An uncommitted segment can be recomputed from the last checkpoint with the same RNG; duplicate compute time must not become duplicate committed history.
6. Keep new checkpoint blobs immutable and preserve old artifacts. Define a new storage/retention manifest and immutable archival tier before exceeding old eight-checkpoint/run-byte/64-attempt caps. Do not disable those checks, delete chain parents or quietly enlarge existing limits. Measure actual checkpoint growth and disk headroom on the representative fixture; test disk-full, partial writes and backup freshness. Hashes detect corruption; authenticating run ownership and the latest tip is separate.
7. Reuse verified compatible Saved Best comparison and original minimization/zero/tie semantics. Cross-weight, cross-input and cross-policy scores remain incomparable. Export JSON/CSV/text from genuine committed results, with segment/run IDs, missing-metric reasons, exact weight/input context and interruption/recovery facts. A cooperative Stop request is not termination until the owned child and supervisor exits are verified.
8. Qualify on a separate fictional realm: uninterrupted versus segmented assignments/fitness/history/best/RNG equality; process restart; crash before/after blob write, commit and acknowledgement; corruption, stale/foreign checkpoint/configuration; old-owner replay; duplicate resume; stop under load; resource/storage exhaustion; exact durable export agreement. Then perform a separately bounded representative stability progression. No duration or checkpoint count by itself proves seven-day safety.

This design preserves mathematics; the unresolved changes are execution-version admission, fixed horizon/stopping interpretation, ownership/freshness and storage/retention policy. They need a reviewed contract and actual fault testing before activation. If the research question permits **independent trials collected over seven days**, that is a different experiment and must be explicitly labeled and approved as such; it is not continuous optimization. Adviser-approved methodology remains unverified outside the repository.
